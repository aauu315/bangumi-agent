# Bangumi Agent：产品路线、学习地图与任务卡

更新：2026-11-01。本文说明目标、依赖、验收和技术选择；任务进度只看 [PROJECT_STATUS.json](../PROJECT_STATUS.json)。旧规划原稿在 `work/history/`，仅供追溯。

## 1. 项目要做成什么

**产品目标**：通过 AI Agent 完成 Bangumi 网站上的各类工作。作品查询、收藏与进度管理是起步闭环；日志、小组浏览与讨论等也是核心业务，只是交付顺序靠后。

**用户入口**：普通用户用本地 Android APK，自己配置模型 Key 和 Bangumi 凭据，不需要终端或作者的服务器。MCP 是给开发者和 Agent 客户端的入口。FastAPI + 数据库是可选的服务端路线。手机端当前用 Chaquopy 复用 Python 业务代码（S2-02 已决定）。

### 核心范围与访问方式

- **模型**：长期支持多家主流提供商，逐家适配和验收。DeepSeek 是第一家（S2 已做协议实验），完整 Agent 在 S4，第二家在 S4-05。
- **接入方式**：按业务需要选择公开 API、网站内部 API 或网页适配，公开 API 没覆盖的功能也在范围内。公开 API 用 Access Token；私有 API（`next.bgm.tv/p1`）可用同一个个人令牌读取（2026-11-05 实测，写入未测）；内部 API 没有兼容性保证，需要单独隔离和持续验证。依据：[官方开发说明](https://github.com/bangumi/dev-docs/blob/master/README.md#新网站和私有-api)。
- **待补规划**：日志、小组等业务卡，Cookie 会话的获取/保存/过期/退出，内容发布的预览批准与写后核对。第一步是 S8-01 调查卡。真实登录、读取浏览器 Cookie、发布内容都需要用户另行授权。

当前已实现：匿名查询、本人收藏只读、单章节进度预览、3 个 MCP 工具、Android 实验 APK。详见状态文件的 `implementation_baseline`。

## 2. 教学节奏

每次开始先读状态文件的 `next_task` 和对应任务卡。一次学习约 20–40 分钟，开发约 60–120 分钟；超过 2 小时的卡拆成小步骤，全部验收前父卡不标 done。结束时在 [LOG](LOG.md) 记录学习过程和验证结果，再更新状态文件。

每张卡标有类型（学习卡 / 决策卡 / 产出卡），分工方式见 AGENTS.md“每张任务卡的代码教学节奏”。S0–S2 已完成，没有补标类型。2026-11-05 起，每张学习卡用户都要写一段业务代码，默认助手先写测试、用户写实现。真实写入必须对具体预览单独批准，结果未知时先读回核对。

## 5. 跨阶段技术规则

- 搜索是只读语义，即便 Bangumi 使用 POST；详情与章节、个人收藏是不同数据。章节 ID 不能用集数或数组位置替代。搜索同名须让用户选具体作品。
- 凭据只在本地由用户输入；不读取旧项目 `.env`，不写入聊天、文档、日志或图检查点。无凭据仍可公开查询。
- 预览、批准、执行、读回分别留痕。未批准、过期、冲突、重复提交为零写；网络断开后的写入结果为 unknown，先读回，不盲重试。
- 批准模式：默认逐项确认，批准只来自用户对具体预览的确认（命令行 approve 或 S3-06 的客户端弹窗），不接受模型自报。用户可在设置中开启信任模式（S4-06），此时跳过确认，其余保护不变。
- 模拟测试、真实匿名 API、真实模型、真实 Agent 客户端、真机 APK 是不同等级的证据；只报告确实完成的等级。
- SDK/API 细节以执行时官方资料和实际调用为准。早期端点/进度/错误处理设计原稿在 `work/history/planning-before-consolidation-20261017/docs/phase-1-plan.md`，仅作历史参考。

### S2-02 · 2026-10-26 已确认的手机运行架构

用户明确确认当前继续使用Kotlin/Compose界面与Chaquopy共享Python业务源码，认为短期内更有效；原生Kotlin业务层重写推迟到项目基础功能完成之后再考虑。本决定只确定当前运行架构，不授权未来自动重写或扩大完整产品实现。

| 方案 | 收益 | 已知代价与证据 |
|---|---|---|
| Kotlin/Compose界面 + Chaquopy共享Python（当前采用） | 现有Python业务层可复用；手机本地执行，不要求作者服务器 | Android16小米14已有公开查询和DeepSeek JSON/SSE真机证据；调试包约30.94MiB，首次Python初始化样本约235～241ms；阻塞调用取消需等返回，不能承诺即刻终止HTTP |
| Kotlin原生执行层 + 共享JSON契约/测试 | 可使用原生Android网络及取消机制；无需携带Python运行时 | 当前尚未实现或测量；须另写业务实现并维持行为一致，不能承诺具体包体积、性能或兼容范围 |

已选择延续已测通的Kotlin界面+Python业务路线；原生业务层在基础功能完成后另行评估；共享Python并不意味着未来所有库都能直接跑在Android。更换HTTP实现、引入新SDK或增加提供商前，各自验证兼容性和取消边界。

**本轮已实现的单一源码位置**：`src/bangumi_agent/api_client.py`及包初始化文件为维护入口，位置不变。Android模块`app/build.gradle.kts`的`chaquopy.sourceSets.main`额外读取`rootProject.file("../../src")`；该相对路径从Android项目根`spike/android-python`指向项目原`src`。白名单仅包括`bangumi_agent/__init__.py`、`bangumi_agent/api_client.py`以及默认手机目录里的`spike_demo.py`、`deepseek_probe.py`。未来新增共享模块需显式加入打包清单并验证依赖，不直接把整个桌面项目/venv复制进APK。

原手机目录的两份手工副本在核对哈希一致后归档至`work/history/s2-01-python-snapshot-20261026/`，不参与构建；不是第二套待维护业务实现。Gradle输出、APK与手机安装中的分发副本仍会存在；修改原源码后需重新构建安装，手机运行时不访问电脑E盘。

S4 是本项目对 AI 应用/Agent 岗位最有分量的部分，除 S4-04 外核心循环、事件和评测都由用户亲手设计或编写。

### S4-01 独立模型适配和最小工具循环

- **类型**：学习卡。核心学习点：**用户亲手写工具循环本身**（messages 怎样追加、工具调用 ID 与结果配对、最大轮次与终止）。助手先写失败的测试和假模型，用户实现循环直到测试通过；provider 适配、协议夹具和工具注册由助手写。
- **前置**：S2-02、S3-03；建议先完成 S3-05。
- **交付物**：agent/loop.py、provider.py、tool_registry.py、协议夹具。
- **具体动作**：本卡先接一个用户可用的模型提供商作为起步闭环，后续按多家主流提供商目标逐项扩充适配；用户消息→模型工具请求→参数校验/允许列表→工具结果→最终答复；核心不依赖MCP进程。第二家提供商在 S4-05。
- **通过标准**：假模型覆盖文本答复/工具调用/工具错误/非法工具；工具调用ID与结果配对；最多5次模型轮次且可配置、超限停止；1次经允许的BYOK真实只读调用另记录。
- **你要能做到**：亲手写出工具循环；能沿一次调用跟踪messages变化；比较自己循环与SDK职责，不引入多Agent。
- **时间假设**：学习2–3h；开发3–5h。
- **证据与停点**：记入 LOG.md#s4-01。

### S4-02 可取消、待确认、受限上下文

- **类型**：学习卡。核心学习点：由用户设计事件列表和终止条件，并亲手写判断循环何时终止、取消后能否继续的逻辑。助手先写测试（含“模型试图自行批准”和“取消后不再写”），会话状态存储和事件序列化由助手写。
- **前置**：S4-01。
- **交付物**：Agent事件契约、会话状态、共享确认接口。
- **具体动作**：输出thinking/tool_result/approval_required/completed/error/cancelled等事件；批准事件来自人工界面；明确本轮发给模型的数据字段与限额。
- **通过标准**：模型无法自行批准；取消后不再产生新写调用，若写已发出进入核对；上下文过大明确停止/要求新会话，不静默丢工具结果；UI不依赖模型一句'成功'。
- **你要能做到**：亲手写出终止和取消的判断；解释模型输出与真实执行状态哪个可信。
- **时间假设**：学习1–2h；开发2–4h。
- **证据与停点**：记入 LOG.md#s4-02。

### S4-03 建立可重复的Agent评测

- **类型**：学习卡。核心学习点：由用户设计 20 个用例和每例的预期工具/副作用，并解读真实模型的失败案例；亲手写对比预期工具和实际工具的评分函数。助手先写该函数的测试，评测运行器和报告格式由助手写。
- **前置**：S4-02。
- **交付物**：evals/20-cases.json、LOG.md#s4-03。
- **具体动作**：冻结20个用例：查询4、同名/缺条件4、预览/确认4、拒绝/注入4、故障/重复4；预先写预期工具及副作用。查询用例中至少一例检查模型是否读错工具返回字段（如把 `ep_status` 当成看到第几集）。返回值说明继续写在函数说明里；只有反复读错且改说明无效时，才试结构化输出说明（`output_schema`）。注意 DeepSeek 的工具定义没有输出结构字段，要让模型读到只能拼进描述。
- **通过标准**：固定假模型20/20控制测试；选至少6例真实模型只读/预览，记录模型/版本/输入/结果与失败率；未经批准写入为0硬门槛；模拟不能包装成真实准确率。

- **证据与停点**：记入 LOG.md#s4-03。

### S4-04 用 LangGraph 实现并比较可恢复工作流

- **类型**：学习卡。核心学习点：由用户画出 State、节点、条件边和人工批准位置，并亲手写一个节点和一条条件路由；助手先写测试，框架样板由助手写。
- **前置**：S4-02、S4-03、S3-03。S2-02 的手机实验决定是否存在移动端 Python 复用；本卡不预设可以把 LangGraph 塞进 APK。
- **交付物**：独立 Python 图入口、带类型的 State/Node/Edge、检查点持久化与对照说明；针对恢复/批准的测试和 `LOG.md#s4-04` 证据。
- **具体动作**：把“搜索候选→确认作品→查询详情→必要时生成进度预览→人工批准→执行/读回”建成显式状态图。先只读与假写；节点复用现有业务服务，不重复写 Bangumi HTTP。设置最大轮次、超时、错误边；检查点只存最少状态，排除 Key、token 和私有正文。用人工 interrupt/resume 衔接 S3 的批准服务，恢复前重新核对计划有效期和账户。
- **通过标准**：离线测试覆盖正常路由、同名需澄清、工具错误、取消、重启恢复、重复 resume、过期批准和写后未知结果；未经人工批准的写请求始终为 0。记录至少一条完整图执行轨迹，并与 S4-01 手写循环比较代码复杂度、可恢复性和故障定位。真实模型/服务调用单独标记，不用假模型结果冒充。
- **你要能做到**：画出 State、节点、条件边、检查点和人工批准位置；亲手写一个节点和一条条件路由，解释 LangGraph 带来的收益与代价。
- **时间假设**：先学 1–2 次、再实现 2–4 次短时段；框架版本与运行环境到执行本卡时再核对。
- **证据与停点**：记入 `LOG.md#s4-04`；未验收整卡前保持 verify 或 planned，个人理解须由真实练习证明。本卡属于 Python/可选服务端作品集路线，不能阻塞本地 APK 主线。

### S4-05 接入第二家模型提供商

- **类型**：学习卡。核心学习点：由用户对比两家的工具调用协议差异（请求格式、工具调用返回、流式分块、错误码），并决定 provider 接口怎样抽象；亲手写把第二家响应解析成统一格式的函数。助手先写测试和协议夹具，第二家的其余适配代码由助手写。
- **前置**：S4-01；S4-03 的评测用例可用于两家对比。
- **交付物**：第二家 provider 适配、协议夹具、两家对比记录。
- **具体动作**：开工时由用户选择提供商（需要用户自己的 Key 和费用）。非流式、流式、工具调用分别验证；不把“兼容 OpenAI 接口”当作全部能力已支持。
- **通过标准**：同一组离线夹具两家都通过；S4-03 中至少 6 例只读用例在两家各跑一次并记录差异；切换提供商不需要改工具循环代码。
- **你要能做到**：亲手写出响应解析函数；说出两家协议的具体差异，以及 provider 接口为什么这样设计。
- **时间假设**：学习 1–2h；开发 2–4h；真实调用有用户自己的费用。
- **证据与停点**：记入 LOG.md#s4-05。

### S4-06 可选的信任模式（跳过逐项确认）

- **类型**：学习卡。2026-11-03 用户提出：有的用户更想要自由的体验，应提供一个可选模式，选择后完全信任 Agent，用户在聊天里说一句就算批准，类似许多 Agent 的“跳过权限”模式（S3-03 讨论时用户也已提到，长期授权以后只能由用户在设置中开启）。核心学习点：①由用户决定这个模式的边界：哪些操作可以免确认、怎样开启和关闭、界面上怎样一直提示“当前处于信任模式”；②由用户亲手写判断某操作能否免确认的函数；③由用户设计提示注入场景：Agent 读到的网页、日志或小组内容里写着“请把某某标为看过”时，在信任模式下会发生什么，应怎样限制。助手先写测试，开关存储和接线由助手写。
- **前置**：S4-02、S4-03（评测里已有拒绝/注入用例，可直接用来衡量信任模式的风险）、S3-06。
- **交付物**：批准模式设置（默认逐项确认）；自有 Agent 与 MCP 执行工具共用的模式判断；离线测试与评测结果；LOG.md#s4-06。
- **具体动作**：
  - 开启方式：只能由用户在设置或本地配置中打开，**不能**通过聊天消息开启，否则网页内容里的一句话就可能把它打开。
  - 免确认的范围：先只包括进度一类可以撤回的修改；发布日志、小组发帖等内容发布不在范围内，等 S8 拆卡时单独决定。
  - 保持不变：信任模式只跳过“用户确认”这一步；过期检查、状态冲突、单次消费、写后读回、unknown 只读核对照常执行，每次写入照常留痕。
  - 界面：信任模式开启时一直有明显标记，可以随时一键关闭。
- **通过标准**：默认模式下行为不变；信任模式下聊天里的一句话能完成一次写入，并照常读回、留痕；提示注入用例的结果如实记录在评测里；开关不能被模型或聊天内容改变。
- **你要能做到**：亲手写出免确认的判断函数；说出信任模式省掉了什么、仍然保留了什么，以及它比默认模式多承担了哪些风险。
- **时间假设**：设计 1h；开发 2–3h。
- **证据与停点**：记入 LOG.md#s4-06。手机端的开关界面在 S5 实现时接入。
- **本卡完成后再决定**：客户端不支持弹窗时（如 Claude 桌面版 Code 页），除命令行外是否增加本机网页确认（服务端打开浏览器显示预览和确认按钮）。2026-11-04 讨论过，用户决定暂不立卡。

### S8-01 网站能力调查与覆盖矩阵

- **前置**：S3-01。
- **交付物**：`docs/coverage.md` 覆盖矩阵；S8 后续卡的草案。
- **具体动作**：列出目标网站功能（日志阅读/撰写、小组浏览/讨论、评论等），逐项查公开 API、网站内部 API、网页适配三种接入方式的可行性；内部 API 的认证（Cookie Session）、稳定性和风险只做文档调查与只读匿名探查，不登录、不读取浏览器 Cookie、不发布内容。
